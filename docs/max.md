# Станция Макс (`yandexstation_2`)

Замеры на станции владельца: ревизия с Zigbee (YNDX-00052), прошивка `5000000921`, `io.sdk`
3.367.25. Железо — [вики](https://hackalice.me/devices/station-max/) и
[ревизия с Zigbee](https://hackalice.me/devices/station-max-zigbee/); здесь только то, чего там нет.

## Платформа

- Android 9 (YaOS_X), не Buildroot: нет glibc, alsa-lib и `/system/vendor/quasar`. Демон
  собирается под `aarch64-linux-android` (bionic, NDK).
- devicetree: `model = "Amlogic"`, `compatible = "amlogic, g12a"`, без `yandex,*`. Модель
  определяется по `ro.yndx.quasar.platform` = `yandexstation_2`; ревизия с Zigbee — по узлу
  `/proc/device-tree/zigbee`.
- `/system` и `/vendor` под dm-verity, `/odm` — нет: root-метод владельца живёт в `/odm`
  (`/odm/bin`, init-сервисы в `/odm/etc/init/*.rc`). Свой автозапуск — тоже init-сервисом в
  `/odm/etc/init`; файлы root-метода не трогать.
- `/odm` — ext4, смонтирован только для чтения. Root-метод ставит свои файлы так:
  `mount -o rw,remount /odm`, копирование, `chown 0:0`, `chmod`, `chcon` (у `.rc` —
  `u:object_r:vendor_configs_file:s0`). Его сервисы — `seclabel u:r:shell:s0`, `disabled`, запуск
  по `on property:sys.boot_completed=1`. init читает `.rc` только при загрузке: новый сервис
  известен init лишь после перезагрузки (`getprop init.svc.<имя>` до неё пуст).
- init Android 9 по `stop <сервис>` добивает всю группу процессов сервиса SIGKILL.
- SELinux на станции владельца — Permissive, но не с самой загрузки: ядро стартует в permissive,
  init через ~1.5 с включает enforcing, и только `rootd` root-метода (по `sys.boot_completed`)
  возвращает permissive, примерно через 20 с после `sys.boot_completed` (13 ноября 2026: 49.8 с →
  ~70 с от старта ядра). Сервис, запущенный по `sys.boot_completed`, сначала работает в enforcing:
  `sh` в домене `shell` не может открыть файл с меткой `system_data_file` в `/data`.
- Из ssh (absshd, домен `shell`) `start`/`stop` init не проходят: `failed to set property
  'ctl.start'`.
- absshd создаёт ключ хоста заново при каждом старте, если нет каталога `/data/local/tmp/absshd`
  (в нём `-hostkey host_ed25519` и `-log sshd.log`); ssh тогда при каждой загрузке видит новый
  ключ. С каталогом (`mkdir -m 700`) absshd при следующем старте сохраняет ключ в нём, и дальше
  ключ не меняется (13 ноября 2026).
- absshd не поддерживает scp/sftp: файлы — через `ssh ... 'cat > файл' < файл`.

## Стек Яндекса

- Весь quasar — приложение `com.yandex.io.sdk` (`/system/priv-app/ServicesIosdk`), нативная часть —
  `lib/arm64-v8a/libquasar_daemons.so` внутри APK (несжатая, грузится прямо из APK).
- `pm disable` отказывает (`Cannot disable a protected package`), `am force-stop` процесс не
  убивает; после `kill` его сразу поднимают привязки (`tv.home`, `tv.alice`, `tv.services` и др.).
  Device owner — `com.yandex.tv.services.platform`.
- Микрофон у `io.sdk` отбирается обратимо: `cmd appops set com.yandex.io.sdk RECORD_AUDIO ignore`
  и `kill` процесса — после перезапуска `audioserver` пишет `Request denied by app op: 27`, вход
  свободен. Возврат — `RECORD_AUDIO allow` и снова `kill`.
- Android 9 не даёт двух захватов одновременно: пока пишет `io.sdk`, наш `startRecording` не
  пройдёт.
- Спотер («Алиса», командный) статически влинкован в `libquasar_daemons.so`; символы `spotter_*`
  не экспортированы (есть только строки сообщений). Экспортированы JNI-методы
  `JniAudioSourceNativeMethods_doPushAudioBuffer`, `SpotterServiceProviderNativeMethods_get`,
  `SpotterListenerPluginNativeMethods_registerListeners`.
- `libquasar_gstreamer.so` из того же APK собрана под bionic: `playbin`, `uridecodebin`,
  `souphttpsrc`, `hlsdemux`, `flacdec`, `opusdec`, `qtdemux`, `wavparse`, `appsink`, `appsrc`,
  `openslessink`, `openslessrc`.

## Звук

- ALSA держит HAL `audioserver`; прямой доступ к `/dev/snd` не используется.
- Захват: `AudioRecord`, источник `MIC`, 48 кГц, s16, `setChannelIndexMask(0xffff)` — 16 каналов,
  как у `io.sdk`. Работает из root-процесса `app_process`, если подставить `ActivityThread` с
  `opPackageName` (иначе JNI Android 9 падает на null).
- VQE Яндекса — preprocessing-эффект `audioserver` для источника `mic`
  (`/vendor/etc/audio_effects.xml`, `/vendor/lib64/soundfx/libyandexvqe.so`); он применяется и к
  нашему захвату. Библиотека VQE (`/vendor/lib64/libyandex_vqe_64.so`) — другой ABI, чем
  `libyandex_evil.so` Buildroot-станций: `YandexVqeC_Init`, `YandexVqeC_ProcessAudio`,
  `YandexVqeC_SendProtobufCommand`.
- Каналы захвата (тон 440 Гц амплитудой 0.05 на динамике и речь с 1-2 м; уровни — RMS в дБFS,
  тон — RMS его составляющей):

  | Канал | Содержимое |
  |---|---|
  | 0 | канал 1 × 30 (`omniChannelGainCoefficient` пресета, +29.5 дБ); пик речи −15 дБFS |
  | 1 | выход VQE `vqe_0`: речь −62 (на микрофонах −60), тон −128 (на микрофонах −69) — эхо подавлено на ~57 дБ; шум −91 |
  | 2 | `vqe_bnr`: речь ослаблена сильнее шума |
  | 3-10 | сырые микрофоны: шум −81, речь −60, тон −69 |
  | 11-12 | аппаратная петля: тон −83, речи нет |
  | 13-14 | цифровой опорный сигнал динамиков L/R: тон −33 при громкости 20/100 |
  | 15 | нули |

  В `quasar.cfg` `io.sdk` каналы распознавания и спотера — `vqe`.
- В первые ~0.5 с после старта захвата — щелчки до 0 дБFS на всех каналах.
- Воспроизведение: `AudioTrack` из root `app_process` работает. Громкость `STREAM_MUSIC` 0..100
  (у владельца 20).
- AAudio из нативного root-процесса (usage `MEDIA`, громкость `STREAM_MUSIC`): поток 48 кГц, s16,
  2 канала открывается за 5–8 мс. `LOW_LATENCY` не выдаётся, режим `NONE` идёт через legacy
  `AudioTrack` (блокирующая запись в нём игнорирует таймаут, по коду AOSP Android 9); burst 1026,
  буфер 2052 кадра (при 44.1 кГц — 629 и 1888). Один xrun на старте и в конце потока.
- Отметки времени AAudio (`getTimestamp`, `CLOCK_MONOTONIC`): первые ~150 мс после старта они не
  про динамик — позиция стоит (1024 кадра), прыгает или идёт вровень с позицией чтения микшера
  (задержка по ним 18–34 мс вместо ~140). Настоящие идут вместе с часами и отстают от прочитанного
  микшером (`getFramesRead`): этот кадр звучит через 124–136 мс (среднее 132 мс по 32 замерам);
  последний записанный кадр — через 134–164 мс.

## Светодиоды и экран

- Кольцо — `/dev/graphics/fb5`, 24×1, 24 бита, порядок байтов B, G, R (проверено 13 ноября 2026:
  байты `40 00 00` на всех пикселях дают синее кольцо); кадр — простая запись 72 байт в
  устройство. Позиция светодиода 0 и направление обхода не определены.
- Экран — `/dev/graphics/fb4`, 25×16, RGB24, stride 75; строка 0 — верхняя; кадр — простая запись
  1200 байт. `io.sdk` рисует часы прямо в `fb4` (содержимое меняется раз в минуту) и держит `fb4`,
  `fb5`, `/dev/input/event{0,2,3}` и `/dev/lp_uart` открытыми.
- Кольцо рисует нативный код `io.sdk` (`libquasar_daemons.so`, `platforms/yandexstation_2`,
  3.367.25): находит framebuffer по имени `YNDX LED ring`, пишет кадр в `mmap` и делает
  `FBIOPAN_DISPLAY`; кадры только по событиям, в покое не пишет ничего. Те же светодиоды видны как
  `station2:{red,green,blue}:ring1..24`; `io.sdk` их не трогает.
- Яркость кольца `io.sdk` задаёт через `/sys/class/backlight/fb5/brightness` (0..255) по датчику
  освещённости `/sys/bus/iio/devices/iio:device0`; кадры не масштабирует.
- Шаблоны — текстовые файлы `/data/data/com.yandex.io.sdk/files/system/ledpatterns/*.led`
  (те же, что `assets/quark/ledpatterns/` в APK). Строка кадра — 24 цвета `RRGGBB` и длительность в
  мс; директивы `loop` (начало повтора), `smooth N` (переход к новому цвету — N+1 шагов линейно,
  отбрасывая дробь, за время кадра), `gradient i1 c1 i2 c2 мс` (заливка всего кольца по индексам
  светодиодов), `gammacorrection` (таблица `ceil(255·(v/255)^2.8)` на все кадры), `rotate`, `fill`,
  `unfill`, `step1`, `step2`, `logsmooth`, `no_size_optimization`; `#` в начале строки —
  комментарий. Столбец `c` шаблона — пиксель `23−c` в `fb5`. Эталон — `probes/ledpattern/ledref.py`.
- Состояния Алисы на кольце (переходы — резкая смена, без перетекания; с подпиской «Алиса Про»
  `io.sdk` берёт `alice_pro_*.led`, pulsar-max — всегда обычные):

  | состояние | шаблон |
  |---|---|
  | слушание | `alice_listening.led`: 340 мс, затем держится последний кадр, повёрнутый к говорящему по направлению звука; без направления угол при первом слушании идёт 45° → ~3° за ~0.3 с и держится (сдвиг ~0.2 светодиода) |
  | обработка | `alice_thinking.led`, повтор 1.36 с |
  | ответ | `alice_speaking.led`, повтор 1.36 с |
  | будильник, таймер | `timer.led`, повтор ~9.4 с; важнее состояний Алисы |
  | ошибка настройки | `error.led`, 3 с |
  | выключение микрофонов | `mute_mics.led` поверх, обрывается через 960 мс |
  | включение микрофонов | кольцо чёрное 960 мс |
  | покой | чёрное |

  После наложения (микрофоны, громкость) фон продолжается с текущего места; состояние, начатое под
  наложением, начинается с первого кадра.
- Громкость крутилкой: уровень из `volume.led` 500 мс, затухание до чёрного, всего 1000 мс (на сколько
  показ отстаёт от щелчка, не замерено); затем
  `io.sdk` рисует своё фоновое состояние (без микрофона — чёрное).

## Кнопки и микрофоны

- `/dev/input/event0` (`gpio_keypad`): кнопка Алисы `KEY_VOICECOMMAND` (582) — нажатие 1,
  отпускание 0, автоповтора нет; переключатель микрофонов `SW_MUTE_DEVICE` (14): 1 — выключены,
  0 — включены. Красную индикацию выключенных микрофонов даёт не `io.sdk`: она есть и при захвате
  устройства.
- `/dev/input/event2` (`rotary-volume`): щелчок крутилки — `KEY_PAGEUP` (громче) или
  `KEY_PAGEDOWN` (тише), нажатие и отпускание с одной меткой времени. `io.sdk` сам меняет
  `STREAM_MUSIC` и показывает громкость на кольце, в том числе без микрофона.
- `/dev/input/event3`: `SW_HEADPHONE_INSERT`.
- `io.sdk` реагирует на кнопку Алисы и без микрофона (фиолетовое кольцо, «Привет, это Алиса»).
  Под `EVIOCGRAB` на `event0` реакции нет, события получает только захватчик; монопольно никто
  устройства не держит.
- Звуки стока: `/data/data/com.yandex.io.sdk/files/system/sounds/common/` (`spotter_start.ogg`,
  `spotter_cancel.ogg`, `error.wav`, `timer.wav`, `volume_change.wav` и др.).

## Ключевое слово

### Спотер «Алиса» стока

Восстановлен по `libquasar_daemons.so` из APK `io.sdk` 3.367.25 (ноябрь 2026); эталон на Python —
`probes/spotter/proto.py`.

- Модель: каталог из `spotter.json` с типом `activation/alisa`
  (`/data/data/com.yandex.io.sdk/files/data/data/spotter_model/<uuid>/`): `model.tflite`,
  `flags.txt`, `words.txt`. TFLite только на стандартных операциях, int8; вход `frames`
  `[1,1,6,80]` float, 9 int8-состояний `state_k` -> `state_k_new`, выход `logits` `[1,1,6,2]`.
  `tract` модель не исполняет (нет `QUANTIZE`); на станции её исполняет `libtflite.so` из того же
  APK (зависит только от `libc`, `libm`, `libdl`, `liblog`). Библиотека хранится в APK без сжатия и
  выровнена по странице: `dlopen("<apk>!/lib/arm64-v8a/libtflite.so")` работает и из процесса в
  `/data/local/tmp`. Стандартный `TfLiteInterpreterCreate` этой сборки падает (резолвер операций
  пустой); `io.sdk` создаёт интерпретатор так: `TfLiteInterpreterOptionsCreate`,
  `SetNumThreads`, `TfLiteAddCustomOpsRegistrators(options)`,
  `TfLiteCustomOpResolverCreate("SPOTTER_ACTIVATION")`,
  `TfLiteInterpreterCreateWithCustomResolver(model, resolver, options)`. Загрузка 9 мс, вызов на
  6 кадров (60 мс звука) 4.2 мс в одном потоке (13 ноября 2026).
- Признаки, на каждый канал: отсчёты int16 без масштабирования; дизеринг `0.1 * T[i]`, где `T` —
  `numpy.random.RandomState(42).randn(2048)` (float32), индекс общий для каналов: 400 отсчётов
  кадра `vqe`, затем 400 кадра `vqe_bnr` того же шага, и не сбрасывается; вычитание среднего кадра; предыскажение 0.97 в форме Kaldi; окно povey
  на 400 отсчётов (25 мс), шаг 160 (10 мс), начало как `snip-edges`; дополнение нулями до 512, FFT,
  мощность; 40 треугольных mel-фильтров Kaldi (1127·ln(1+f/700)), 20–8000 Гц; натуральный логарифм
  без нижнего предела. CMN нет: пустой `feat-pipeline` в `flags.txt` отключает встроенный `cmn:lda`.
- Вход модели на кадр: `[vqe (канал 1) 40 | vqe_bnr (канал 2) 40]`. Вызов — 6 новых кадров без
  перекрытия; состояния стартуют с нулевых точек квантизации и копируются с выхода; после старта и
  сброса отбрасывается столько выходных кадров, сколько записано в метаданных модели
  `right_context` (`Model.metadata` TFLite; у «Алисы» 16, у модели VAD 11).
- Решение (`chen14`): `p = softmax(logits)[1]`; сглаживание — сумма за 5 кадров, делённая на
  `min(5, n+1)`, где `n` — номер кадра с 1 (первые 4 кадра делятся на 2…5); уверенность — максимум за 20 кадров; срабатывание — первый кадр с уверенностью
  строго больше 0.861 (`thresholds`), повтор — только после спада до 0.861 и ниже; 0.435
  (`subthresholds`) — предварительное срабатывание, к активации не ведёт.
- Ещё одна ступень стока — блокировщик на время собственного TTS (`use-tts-blocker true`,
  `tts-timings-info/` в каталоге модели): во время речи `io.sdk` превращает срабатывание в
  предварительное. Не восстановлен: он завязан на TTS `io.sdk`, а ответы pulsar-max идут из HA.
- Ключи `flags.txt`, меняющие решение, которых у этой модели нет: `spotter-tflite-activation-function`,
  `spotter-npu-stride`, `fire-at-subthreshold-phrases`, `fire-at-two-subthresholds-phrases`,
  `counteractivation-features-enabled true`.
- На речи владельца без «Алисы» (запись 12 ноября) уверенность не выше 0.125.

### Команды стока

Восстановлены по `libquasar_daemons.so` из APK `io.sdk` 3.367.25 (ноябрь 2026); эталон на Python —
`probes/spotter/cmd_ref.py`.

- Модель: каталог из `spotter.json` с типом `command` (модель
  `ru-RU-quasar-commands-30Apr25-...`): `acoustic_model.nnet`, `flags.txt`, `words.txt`. Это не
  TFLite, а двоичный Kaldi nnet3 со слоями Q16 (`<S>` — масштаб матрицы, `SIM` — её значения int16),
  который `io.sdk` исполняет своим движком: вход 40 log-mel, `FixedBias` и `FixedScale` (CMVN внутри
  сети), 7 блоков SVDF (проекция без смещения, причинная свёртка по времени по каналам со
  смещением, hardswish, ещё проекция и hardswish), две головы softmax на 22 и 6 выходов, склеенные
  по порядку `words.txt`. 0.88 млн весов, 0.88 млн умножений на кадр.
- Признаки — как у «Алисы», но один канал `vqe` (без `bnr`); дизеринг идёт по той же
  последовательности, 400 отсчётов на кадр.
- 28 выходов: два класса тишины и 26 слов; 25 команд, из них 6 из двух слов (включи / выключи свет,
  телевизор, блютуз). Слова: дальше, назад, выше, ниже, вправо, влево, вверх, вниз, домой,
  продолжи, играй, стоп, хватит, пауза, следующий, громче, тише, лайк, дизлайк и составные.
- Решение — `chen14` на несколько слов: на каждое слово команды сумма за 8 кадров (`w-smooth`), с
  тем же делителем `min(8, n+1)`, что у «Алисы»; максимум слова ищется за 60 кадров (`w-max`),
  начиная с пика предыдущего слова; уверенность — среднее геометрическое максимумов слов; порог
  свой у каждой команды (`subthresholds` равны `thresholds`, предварительных срабатываний нет).
  Срабатывание — лучшая команда выше порога (по отношению уверенности к порогу), сменившаяся с
  прошлого кадра; после него 35 кадров пропуска и обнуление буферов. Поверх — 1200 мс между
  срабатываниями, как в pulsar.
- `io.sdk` включает команды по директиве сервера и по группам из настроек пользователя;
  pulsar-max, как pulsar, слушает их всегда, кроме выключенных микрофонов.
- Запись владельца (13 ноября 2026, 1–2 м, тишина, без «Алисы», каждое из 10 слов pulsar дважды):
  16 срабатываний из 20, все верные, ложных нет. Оба «стоп» не дотянули до порога 0.761
  (уверенность 0.39 и 0.66), поэтому «Алиса, стоп» ловится и по тексту HA.
- pulsar-max считает проекции сети как `io.sdk` (`dynamically-quantized-matmul`): веса int16 со
  своим масштабом, вход каждого кадра приводится к int16 на лету, накопление в int32, пачками по 6
  кадров (`am-batch-size`); свёртка — во float. Вероятности отличаются от расчёта во float не больше
  чем на 0.0024, срабатывания на записи те же.
- На станции (4 × Cortex-A53, NEON без `asimddp`) обе модели — 16.2 с процессора на 74.5 с звука
  (`--spot`; во float было 23.2 с). Вживую в покое поток спотеров — 19% одного ядра (во float 28%),
  из них команды около 8%; весь демон — 23%.

### Частотный фильтр стока

Защита от «Алисы» из рекламы: гасит срабатывание, если в звуке перед ним есть узкие провалы спектра
на 8 частотах (3501, 2089, 814, 1355, 638, 4510, 2635, 486 Гц). Эталон —
`probes/spotter/freqfilter.py` и `probes/spotter/gate.py`.

- Канал — один сырой микрофон (у Миди `RAW_MAIN_MIC_SYNC`); какой микрофон Макс сток считает
  «лучшим», не установлено.
- Кадр 252 мс (4032 отсчёта), шаг 177 мс; дизеринг, вычитание среднего, предыскажение 0.72, окно
  povey, FFT 4096, мощность.
- На частоту `f`: среднее мощности в полосе вокруг `f` минус (в логарифме) меньшая из медиан полос
  вокруг `0.68f` и `1.45f`; полуширины 3 и 99 бинов, масштабируются с частотой. Оценка кадра —
  сумма по 8 частотам.
- На срабатывание: минимум оценок 5 кадров (960 мс), кончающихся не позже момента срабатывания;
  если он не больше -3.6, срабатывание становится предварительным. Состояние не сбрасывается.
- На речи владельца худшее значение -1.0 (сырые микрофоны, каналы 3–5).

## Zigbee

- Радио — Telink B91 с прошивкой шлюза Яндекса (`assets/quark/zigbee/gateway.ybl` в APK, контейнер
  `.ybl` того же семейства, что у Миди: magic `KNLT`, производитель 0x140A). Протокол — Telink
  zbhci с расширениями Яндекса (`telink_ncp.cpp`), не EZSP и не ZNP; UART 115200 8N1 без
  управления потоком, `/dev/zigbee_uart` → `/dev/lp_uart`.
- Сброс и загрузчик — через `zb_control` (`/sys/devices/platform/zigbee/zb-reset`, `zb-boot`);
  обновление прошивки радио `io.sdk` делает сам при расхождении версии.
- `io.sdk` — координатор сети; в `files/data/data/zigbee/` у него `network.dat` (protobuf
  `TNetworkParameters`: PAN, ключ, канал, узлы), `device.lmdb`, `ota.lmdb`. На станции владельца в
  сети есть привязанные устройства.
- `io.sdk` включает Zigbee, только если существует `/dev/zigbee_uart` (Java
  `shouldEnableZigbee`); без него и после перезапуска `io.sdk` порт свободен (вывод из кода, не
  проверено). Облако Яндекса при этом может удалить устройства станции (`syncEndpointsRemoveEnable`).
- ZHA и Zigbee2MQTT протокол zbhci не понимают: отдать радио HA можно только своей прошивкой
  координатора (как `radio/` pulsar для Миди) с перепривязкой устройств; совместимость образов pulsar
  с модулем Макс не проверена.
